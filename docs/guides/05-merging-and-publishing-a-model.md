# Guide 05 — Merging a LoRA Adapter and Publishing It

Day 8 turns the trained adapter into a model other people can actually use. Two steps that
look like plumbing but each hide a real decision: **merging** and **the model card**.

## What merging actually does

Training produced a ~190 MB adapter, not a model. It holds only the `A` and `B` matrices from
Guide 04 — useless without the 3B base model they modify. At inference, PEFT computes:

```
output = x @ W_frozen  +  (alpha / r) · (x @ A.T @ B.T)
```

Two matrix multiplications per adapted layer instead of one, across 196 adapted modules.
Merging folds the update back into the base weights, once, ahead of time:

```
W_merged = W_frozen + (alpha / r) · B · A
```

After that the model is architecturally identical to stock Llama-3.2-3B — same shapes, same
forward pass, no PEFT dependency, no per-layer overhead. It loads with a plain
`AutoModelForCausalLM.from_pretrained()`.

The merge is **exact**, not an approximation: `B·A` is a real matrix of the same shape as `W`,
and adding it changes nothing about what the model computes. Inference output is identical to
the adapter path, modulo floating-point ordering.

## The 4-bit trap

Here is the part that trips people up. Training loaded the base model in 4-bit NF4. The
obvious move — load 4-bit, call `merge_and_unload()`, save — is wrong, and it fails quietly by
degrading quality rather than raising an error.

Why: the 4-bit weights are a *lossy compression* of the originals. Merging into them means
dequantizing to fp16, adding `B·A`, then re-quantizing to 4 bits. That second quantization
round-trips the adapter's contribution through a 4-bit grid, and the fine-tuning signal — a
small, precise update — is exactly the kind of thing that gets rounded away.

So the merge runs in **fp16 against the original base weights**:

```
load base in fp16 (not quantized)  ->  apply adapter  ->  merge  ->  save fp16
```

This needs ~6.4 GB for the base plus headroom for the merged copy. It runs comfortably on a
Kaggle GPU, and also on CPU with enough RAM if you're patient — no GPU is strictly required,
since merging is a handful of matrix additions rather than a training run.

Quantization for deployment, if wanted, happens **after** the merge, from the fp16 weights.

## Adapter or merged model — publish which?

Both, and for different reasons:

| | Adapter (~190 MB) | Merged (~6.4 GB) |
|---|---|---|
| Download size | Small | Large |
| Needs `peft` | Yes | No |
| Needs base model access | Yes — Llama-3.2 is gated | No |
| Swappable with other adapters | Yes | No |
| Inference overhead | Slight | None |

The adapter is the honest artifact — it's what you actually trained, and it's small enough to
version freely. The merged model is the *usable* one, especially since Llama-3.2 is gated:
someone without approved access to Meta's repo can't use your adapter at all, but can use a
merged model.

## The model card is not paperwork

A model card is where you say what your model is bad at. Everything else in it is discoverable
from the files; the limitations are not, and they're the part that stops someone deploying
your model into a situation it can't handle.

For this model, an honest card has to state:

- **The test set was generated by the same teacher model as the training data** (Qwen2.5-7B),
  so 91.5 F1 measures agreement with that teacher's answer style, not human ground truth. The
  base-vs-tuned delta is fair; the absolute number is optimistic.
- **~8% of numeric answers are wrong.** In a finance context, that is the number a user most
  needs to know, and it argues for always showing the source context alongside an answer.
- **It answers from context you supply**, and has no live market knowledge. Its training data
  ends at the scrape date.
- **It is not financial advice**, and shouldn't be presented as such.

Writing those down costs nothing and is the difference between a portfolio project that looks
competent and one that is.

## Licensing: the naming rule people miss

Llama 3.2 ships under the **Llama 3.2 Community License**, not a standard open-source licence,
and it carries two obligations that apply the moment you publish a fine-tune:

1. **The model name must begin with `Llama`.** The licence requires derivative models
   distributed publicly to carry `Llama` at the start of the name. So
   `Llama-3.2-3B-finance-india` complies; `finance-chatbot-3b` does not.
2. **Attribution**: display "Built with Llama" and include a copy of the licence with the
   distributed model.

The training data has its own provenance story too — articles scraped from Moneycontrol under
the terms documented in `dataset-design.md`. The card should link there rather than imply the
dataset is unencumbered, and the dataset itself is not redistributed: only derived Q/A pairs
were used, for training.

## Talking points

- *"What does merging a LoRA adapter do?"* — Folds `(alpha/r)·B·A` back into the frozen weights
  so the model is architecturally plain again: no PEFT at inference, no extra matmuls, loadable
  with a normal `from_pretrained`.
- *"Why not merge into the 4-bit model you trained on?"* — Merging into quantized weights
  re-quantizes the adapter's contribution through a 4-bit grid and rounds away the fine-tuning
  signal. Merge in fp16 against the original weights, quantize afterwards if needed.
- *"Why publish both the adapter and the merged model?"* — The adapter is small and swappable
  but requires `peft` and gated access to the base. The merged model is usable by anyone.
- *"What goes in a model card?"* — Mainly the limitations. For this one: the test set shares a
  generator with the training set, ~8% of numeric answers are wrong, there is no live market
  knowledge, and it is not financial advice.
- *"Any licensing constraints?"* — Llama 3.2's licence requires derivative model names to begin
  with "Llama" and a "Built with Llama" attribution.
